\chapter{Estudo de Caso: patch-hub}

Uma vez apresentadas as propostas de adaptação do Modelo de Atores para experimentação fora do domínio dos sistemas distribuídos, chega o momento de realizar um estudo de caso para aplicar a proposta em um projeto real para posterior análise de resultados. 

O projeto escolhido foi uma ferramenta de software livre desenvolvida sob a organização \textit{Kworkflow} (kw) chamada de patch-hub. Neste capítulo, será apresentado o contexto do projeto, a arquitetura original e suas limitações, os objetivos do estudo de caso e a proposta de refatoração do projeto com o uso do Modelo de Atores, cuja implementação estará disponível na íntegra no \href{https://github.com/nahharris/ph-actors-tcc}{repositório do projeto no GitHub}.

\section{Contexto}

Para compreender adequadamente o projeto patch-hub e sua proposta, é necessário entender o ecossistema de desenvolvimento do kernel Linux e os desafios enfrentados pelos desenvolvedores. O Linux é um sistema operacional de software livre baseado no kernel Unix-like desenvolvido por Linus Torvalds em 1991~\citep{linux_wikipedia}. O kernel Linux é o núcleo do sistema operacional, responsável por gerenciar recursos de hardware, processos e comunicação entre componentes do sistema~\citep{kernel_wikipedia}.

\subsection{O Processo de Contribuição para o Kernel Linux}

O desenvolvimento do kernel Linux é um processo colaborativo que envolve milhares de desenvolvedores ao redor do mundo. Devido à sua complexidade e tamanho, o kernel é organizado em subsistemas especializados, cada um com responsabilidades específicas~\citep{kernel_subsystems}. Contribuições para o kernel, conhecidas como \textit{patches}, são tradicionalmente enviadas através de listas de discussão públicas por email e revisadas por mantenedores especializados~\citep{kernel_patches}. 

Essa forma de contribuição é um processo tradicional e bem estabelecido, mas que traz diversos desafios para os desenvolvedores. Os desenvolvedores do kernel precisam se inscrever em múltiplas listas de email e gerenciar um volume considerável de mensagens. Isso dificulta muito acompanhar o status de suas e demais contribuições sendo feitas a um dado subsistema. Essa abordagem também dificulta o ingresso de novos contribuidores, pois é necessário um setup local complexo e dificulta o acesso aos patches enviados antes do novo contribuidor se inscrever nas listas de email.

\subsection{O Projeto lore.kernel.org}

Para mitigar essas dificuldades, foi criado o projeto lore.kernel.org, um arquivo público que fornece uma interface web para visualizar e pesquisar mensagens das listas de discussão do kernel~\citep{lore_api}. O lore.kernel.org oferece uma \emph{API} que permite acesso programático aos \emph{patches} arquivados, incluindo funcionalidades de busca, paginação e filtros avançados.

A \emph{API} do lore suporta consultas complexas através de parâmetros de \emph{query string}, permitindo filtrar \emph{patches} por critérios como assunto, autor, data e conteúdo. Esta funcionalidade é fundamental para ferramentas que buscam automatizar ou simplificar a interação com o ecossistema de \emph{patches} do kernel.

\subsection{O Projeto Kworkflow}

O kw é descrito como uma \textit{Developer Automation Workflow System} (DAWS) que visa reduzir a sobrecarga de configuração e fornecer ferramentas para tarefas comuns do desenvolvimento de kernel.

O projeto é um utilitário de terminal que oferece um conjunto de funcionalidades em uma interface unificada para diversas operações como compilação, deploy, debug e gerenciamento de configurações, consolidando ferramentas anteriormente dispersas como pode ser visto na tabela \ref{tab:kw-commands}.

\subsection{O patch-hub}

O patch-hub (veja a sua interface na figura \ref{fig:patch-hub-original}) é uma ferramenta desenvolvida como parte do ecossistema do kw, especificamente projetada para interagir com a \emph{API} do lore.kernel.org~\citep{patch_hub_github}. Sua missão é agilizar a navegação e revisão de contribuições para o kernel Linux, fornecendo uma interface de usuário baseada em terminal (\emph{TUI}) que simplifica o processo de descoberta, análise e acompanhamento de \emph{patches}.

A ferramenta permite aos desenvolvedores navegar por listas de patches, aplicar filtros de busca, visualizar conteúdo de patches e gerenciar seu fluxo de trabalho de revisão diretamente do terminal, eliminando a necessidade de alternar entre interfaces web e ferramentas de linha de comando.

A implementação do patch-hub (tanto a original quanto a refatorada) fornece um conjunto de funcionalidades para interagir com o arquivo de \emph{patches} do kernel Linux. O sistema permite a seleção e navegação de listas de discussão arquivadas no \textit{lore.kernel.org}, apresentando os conjuntos de \emph{patches} associados. Ao examinar uma série específica, a interface disponibiliza o conteúdo individual dos \emph{patches} juntamente com metadados relevantes, incluindo título, autor, versão, quantidade de \emph{patches} e \emph{timestamp} da última atualização.

O sistema implementa operações fundamentais para o \emph{workflow} de revisão de \emph{patches}: aplicação de \emph{patches} em repositórios locais do kernel, organização de séries em um sistema de favoritos, e composição de respostas com tags de revisão padrão, como \texttt{Reviewed-by}.

A renderização do conteúdo dos patches é implementada com suporte a múltiplos backends, incluindo ferramentas externas, além de um renderizador padrão. Esta abordagem permite variação na apresentação visual dos patches ao gosto do usuário sem comprometer a portabilidade da aplicação.

\section{Arquitetura Original}

A implementação original do patch-hub seguia uma arquitetura majoritariamente \emph{single-threaded} e monolítica com inspirações no padrão arquitetural MVC. A organização do código era dada em termos dos seguintes módulos:

\begin{itemize}
    \item \textbf{\texttt{lore}}: Interação com a \emph{API} do lore.kernel.org
    \item \textbf{\texttt{ui}}: Renderização de terminal e lógica de exibição
    \item \textbf{\texttt{cli}}: \emph{Parsing} de argumentos de linha de comando
    \item \textbf{\texttt{app}}: Estado central da aplicação e gerenciamento de dados
    \begin{itemize}
        \item \texttt{logger}: Gerencia funcionalidade de \emph{logging}
        \item \texttt{popup}: Cria e gerencia diálogos \emph{popup}
        \item \texttt{config}: Gerencia configurações da aplicação
    \end{itemize}
    \item \textbf{\texttt{handler}}: Manipulação de entrada do usuário e processamento de eventos
\end{itemize}

\section{Limitações da Arquitetura Original}

Apesar de suas funcionalidades, a implementação original do patch-hub apresentava limitações arquiteturais fundamentais que comprometiam sua extensibilidade, manutenibilidade e capacidade de evolução. Essas limitações vinham de decisões de design que, embora funcionais para o escopo inicial, criavam gargalos estruturais que dificultavam a adição de novas funcionalidades e a manutenção do código no longo prazo.

Este cenário reflete o problema discutido no capítulo~\ref{chap:arquitetura-software} com base no estudo de~\cite{kassab2018architectural}: em projetos reais, o foco excessivo no atendimento rápido de requisitos funcionais muitas vezes relega os requisitos de qualidade a um segundo plano. No caso do patch-hub, essa priorização resultou em uma dívida técnica considerável, explicitamente reconhecida em registros de desenvolvimento do projeto, como nas notas de lançamento da versão 0.1.7~\citep{patch_hub_v017}, que destacavam a necessidade urgente de uma rearquitetura para viabilizar a evolução contínua da ferramenta.

\subsection{Gargalo de Mutação Centralizada}

O principal problema arquitetural reside na concentração de todo o estado da aplicação em uma única estrutura \texttt{App} que deve ser passada como \texttt{\&mut App} através de todo o código. Esta abordagem cria um \emph{gargalo de mutação centralizada} que viola princípios de \emph{borrow checking} do Rust.

O sistema de \textit{ownership} do Rust impõe que quando uma função recebe \texttt{\&mut App}, ela adquire uma referência mutável exclusiva de toda a estrutura. Isso significa que:

\begin{itemize}
    \item Nenhum outro código pode ler ou escrever qualquer campo de \texttt{App} até que essa referência seja liberada
    \item Campos não podem ser emprestados independentemente enquanto \texttt{\&mut App} está ativa
    \item Componentes internos não podem modificar componentes irmãos sem liberar a referência primeiro
\end{itemize}

Esta restrição força a centralização de toda lógica de mutação nos métodos de \texttt{App}, impedindo que componentes gerenciem seu próprio estado de forma independente. 

O resultado é uma violação do princípio da responsabilidade única, forçando a estrutura central a conhecer detalhes de implementação de todos os seus componentes. Além disso, o princípio da inversão de dependência também é violado, fazendo com que a estrutura de alto nível dependa diretamente de mecanismos de baixo nível de seus componentes internos.

\subsection{Impossibilidade de Composição Modular}

O design atual impede a composição modular de \emph{handlers} e componentes devido às restrições de \emph{borrowing}. \emph{Handlers} de eventos devem receber \texttt{\&mut App} inteiro mesmo quando precisam acessar apenas um subconjunto específico de dados. Isso cria uma situação onde \emph{handlers} não podem ser decompostos em funções auxiliares menores e também funções auxiliares que precisam de múltiplos campos de \texttt{App} enfrentam conflitos por tentarem pegar referências a partes de algo que já possui uma referência mutável.

Esta limitação força a criação de métodos monolíticos em \texttt{App} que conhecem detalhes de implementação de múltiplos componentes, aumentando a complexidade e reduzindo a testabilidade.

\subsection{Atualizações de Estado Intercomponentes Problemáticas}

A arquitetura torna impossível a atualização direta de estado entre componentes, forçando todas as interações através da estrutura central \texttt{App}. Quando um componente precisa modificar o estado de outro componente irmão, ele deve passar pela estrutura \texttt{App} como intermediário, criando acoplamento forte entre componentes que deveriam ser independentes.

\subsection{Concorrência e Responsividade Limitadas}

A natureza \emph{single-threaded} da aplicação cria gargalos significativos durante operações de I/O, resultando em:

\begin{itemize}
    \item Interfaces não responsivas durante requisições de rede
    \item Bloqueio da UI durante operações de sistema de arquivos
    \item Lógica complexa para implementar telas de carregamento
    \item Impossibilidade de realizar operações paralelas independentes
\end{itemize}

Para contornar esse problema, foi feito uso de mecanismos para paralelizar certas regiões do código. A complicação aqui é que referências em Rust não podem ser compartilhadas entre \emph{threads} pois não há garantias de que uma \emph{thread} vá ser encerrada antes do dono do valor referido, o que poderia causar vazamentos de memória ou condições de corrida indesejáveis.

\subsection{Dificuldades de Testabilidade}

A arquitetura monolítica torna extremamente difícil a criação de testes unitários eficazes. Testes de \emph{handlers} individuais requerem a construção de toda a estrutura \texttt{App}, incluindo dependências que podem não ser relevantes para o teste específico. Isso resulta em:

\begin{itemize}
    \item Testes lentos devido à necessidade de inicialização completa
    \item Testes frágeis que quebram quando componentes não relacionados são modificados
    \item Impossibilidade de isolar comportamento específico para teste
    \item Dificuldade em criar \emph{mocks} e \emph{stubs} para dependências externas
\end{itemize}

Esta limitação compromete significativamente a capacidade de garantir qualidade através de testes automatizados, aumentando o risco de regressões em mudanças futuras.

\section{Objetivos da Reimplementação}

Fica evidente que o patch-hub necessita de refatorações para tentar resolver os problemas supracitados. Em especial, fica notável uma grande necessidade de melhorias do ponto de vista da flexibilidade do sistema. Tendo em vista que o Modelo de Atores proporciona alta modularidade e baixo acoplamento aos sistemas, isso torna o patch-hub um candidato interessante para experimentação e avaliação de valor da proposta. Além disso, o patch-hub toca em domínios suficientemente diversos para que o experimento seja bastante completo.

Este trabalho não criará uma reescrita completa com 100\% de compatibilidade de funcionalidades. Ao invés disso, um subconjunto das funcionalidades foi escolhido para implementação, suficiente para ter as funcionalidades principais do patch-hub, que são:

\begin{itemize}
    \item Uma interface de usuário de texto interativa
    \item Integração com \emph{API} do Lore com suporte a \emph{cache}
    \item Navegar através das listas de discussão catalogadas
    \item Acesso a um feed de patches enviados para uma lista de discussão
    \item Fornecer uma visualização do conteúdo e metadados de um patch
    \item Configurações personalizáveis
    \item Um sistema de log
\end{itemize}

\section{Modelagem com Atores}

Com objetivos estabelecidos, foi feita uma modelagem da arquitetura do patch-hub com o uso de atores que pode ser vista na figura \ref{fig:patch-hub-actors}. A modelagem adota os princípios SOLID como guias. Os atores serão categorizados em 2 grupos considerando o tipo de interação que eles são responsáveis: externas ou internas.

O primeiro grupo é formado pelos atores responsáveis por interações com componentes externos ao sistema, como, por exemplo, o sistema de arquivos, a internet ou o terminal. Este grupo será chamado de atores de integração pois permitem a integração do programa com outros sistemas, gerando, assim, efeitos colaterais no mundo real.

O segundo grupo é formado pelos atores que irão interagir apenas com demais atores, ou seja, componentes internos ao sistema. Este grupo tem uma diferença fundamental no que diz respeito a sua testabilidade. 

Por dependerem apenas de outros atores, testes unitários se tornam triviais uma vez que se criem \emph{mocks}. Ao testar um ator contra \emph{mocks} que imitem o comportamento desejado dos atores de dependência, dá-se a garantia de que apenas o código do próprio ator é o que influencia no resultado dos testes. Este grupo será chamado de atores internos por não interagirem diretamente com sistemas externos.

\subsection{Atores de Integração}

Primeiramente, foi catalogado quais capacidades do patch-hub dependem unicamente de interação com sistemas externos ao programa que serão inclusas na versão reescrita do projeto. As capacidades escolhidas foram:

\begin{itemize}
    \item Operações do sistema de arquivos
    \item Requisições HTTP
    \item Manipulação de variáveis de ambiente
    \item Controle de entrada e saída do terminal
    \item Execução de comandos externos
\end{itemize}

Essas capacidades não fazem parte da lógica de negócio do patch-hub, mas servem de bases para permitir a sua implementação. Cada uma delas pode ser traduzida para um ator em nossa aplicação seguindo os princípios SOLID, especialmente os princípios de responsabilidade única e de segregação de interfaces.

\subsubsection{Sistema de Arquivos}

O ator Sistema de Arquivos é responsável por gerenciar as operações de leitura, escrita, remoção e listagem de arquivos e diretórios. Ele é responsável por garantir que as operações sejam realizadas de forma segura, garantindo que o sistema de arquivos seja consistente e que os arquivos e diretórios sejam gerenciados corretamente.

\textbf{Implementação:} \href{https://github.com/nahharris/ph-actors-tcc/blob/master/src/fs.rs}{\texttt{src/fs.rs}}

\textbf{Mensagens:}

\begin{itemize}
    \item \texttt{ReadFile}: Abre um arquivo apenas para leitura (não cria se não existir)
    \item \texttt{WriteFile}: Abre um arquivo para escrita (trunca conteúdo, cria se necessário)
    \item \texttt{AppendFile}: Abre um arquivo para anexar (cria se necessário)
    \item \texttt{RemoveFile}: Remove um arquivo do sistema de arquivos
    \item \texttt{ReadDir}: Lê o conteúdo de um diretório
    \item \texttt{MkDir}: Cria um diretório e seus pais
    \item \texttt{RmDir}: Remove um diretório e seu conteúdo
\end{itemize}

\subsubsection{Rede}

O ator Rede é responsável por gerenciar as operações de requisição HTTP. Ele é o mecanismo base que vai permitir a integração do sistema com a \emph{API} web do lore.kernel.org.

\textbf{Implementação:} \href{https://github.com/nahharris/ph-actors-tcc/blob/master/src/net.rs}{\texttt{src/net.rs}}

\textbf{Dependências:}

\begin{itemize}
    \item \textbf{Configurações}: Para obter configurações de timeout e outras configurações de rede
    \item \textbf{Log}: Para registrar operações de rede para posterior análise
\end{itemize}

\textbf{Mensagens:}

\begin{itemize}
    \item \texttt{Get}: Executa uma requisição HTTP GET para a URL especificada com headers opcionais
    \item \texttt{Post}: Executa uma requisição HTTP POST para a URL especificada com headers opcionais e corpo
    \item \texttt{Put}: Executa uma requisição HTTP PUT para a URL especificada com headers opcionais e corpo
    \item \texttt{Delete}: Executa uma requisição HTTP DELETE para a URL especificada com headers opcionais e corpo
    \item \texttt{Patch}: Executa uma requisição HTTP PATCH para a URL especificada com headers opcionais e corpo
\end{itemize}

\subsubsection{Variáveis de Ambiente}

O ator Variáveis de Ambiente é responsável por gerenciar as operações de definição, remoção e recuperação de variáveis de ambiente.

\textbf{Implementação:} \href{https://github.com/nahharris/ph-actors-tcc/blob/master/src/env.rs}{\texttt{src/env.rs}}

\textbf{Mensagens:}

\begin{itemize}

\subsubsection{Terminal}

O ator Terminal gerencia o \emph{loop} de eventos da interface de usuário baseada na biblioteca Cursive. Ele mantém uma fila FIFO interna de eventos de \emph{UI} (teclas pressionadas, seleções, etc.) além de ser responsável por desenhar no terminal. Ele também expõe uma \emph{API} baseada em mensagens para atualizar a interface e recuperar os eventos de \emph{UI} ocorridos.

\textbf{Implementação:} \href{https://github.com/nahharris/ph-actors-tcc/blob/master/src/terminal.rs}{\texttt{src/terminal.rs}}

\textbf{Dependências:}

\begin{itemize}
    \item \textbf{Log}: Para registrar eventos do terminal para posterior análise
\end{itemize}

\textbf{Mensagens:}

\begin{itemize}
    \item \texttt{Show}: Atualiza a tela exibida com um novo tipo de tela
    \item \texttt{GetUiEvent}: Recupera o próximo evento de \emph{UI} da fila
    \item \texttt{ClearUiEvents}: Limpa a fila de eventos de \emph{UI}
    \item \texttt{Quit}: Termina a \emph{UI} e sai da aplicação
\end{itemize}

O método \texttt{spawn()} do ator Terminal retorna uma tupla contendo a interface do ator e um \texttt{JoinHandle} que permite que outros atores detectem quando o terminal foi encerrado, permitindo encerramento gracioso da aplicação. Este design evita a necessidade de envolver o \texttt{JoinHandle} em um \texttt{Arc} e simplifica o gerenciamento do ciclo de vida do terminal.

\subsection{Atores Internos}

As demais capacidades foram catalogadas. Dessa vez são capacidades de alto nível, ou seja, que não dependem de detalhes de implementação específicos. Elas vão depender das abstrações feitas para os atores de integração, endereçando, assim, o DIP. As capacidades escolhidas foram:

\begin{itemize}
	\item Registrar eventos com um sistema de logs
	\item Gerenciar configurações
	\item Acessar a Lore API
	\item Suporte a caching das requests feitas
	\item Desenhar a interface do usuário (TUI)
\end{itemize}

\subsubsection{Logs}

Fornece um serviço de \emph{logging} centralizado e \emph{thread-safe}. Ele recebe mensagens de log de outros atores e as escreve em um arquivo de log designado, fornecendo diferentes níveis de log para \emph{debugging} e monitoramento.

\textbf{Implementação:} \href{https://github.com/nahharris/ph-actors-tcc/blob/master/src/log.rs}{\texttt{src/log.rs}}

\textbf{Dependências:}

\begin{itemize}
    \item \textbf{Sistema de Arquivos}: Para persistir logs em um arquivo
\end{itemize}

\textbf{Mensagens:}

\begin{itemize}
    \item \texttt{Log}: Registra uma mensagem com um nível de log específico (Info, Warning, Error) através de uma estrutura \texttt{LogMessage}
    \item \texttt{Flush}: Escreve as mensagens de log em buffer para stderr e encerra o logger
    \item \texttt{CollectGarbage}: Executa a limpeza de arquivos de log antigos baseado na idade máxima configurada
\end{itemize}

\subsubsection{Configurações}

Responsável por carregar configurações de um arquivo de configuração, fornecê-las a outros atores sob demanda e persistir mudanças.

\subsubsection{Cache}

\textbf{Implementação:} \href{https://github.com/nahharris/ph-actors-tcc/blob/master/src/app/cache.rs}{\texttt{src/app/cache.rs}}

A fim de agilizar o acesso a dados diminuindo a quantidade de operações que dependam de chamadas de \emph{API} ou do sistema de arquivos, será feito o uso de técnicas de \emph{caching}.

Para cada domínio de dados, será criado um ator específico que se encarregará de gerenciar o \emph{cache} para esse domínio. Sendo responsável por lidar com \emph{cache misses} e \emph{cache hits}, assim como com a validação de \emph{cache}, garantindo consistência dos dados realizando o mínimo de acessos necessários a sistemas externos.

\textbf{Listas de Discussão}

Armazena em \emph{cache} a lista de todas as listas de discussão disponíveis da \emph{API} do Lore. Ele busca a lista completa, ordena alfabeticamente e a persiste no sistema de arquivos para acelerar inicializações subsequentes da aplicação. Ele gerencia validação de \emph{cache} para atualizar periodicamente a lista.

\textbf{Implementação:} \href{https://github.com/nahharris/ph-actors-tcc/blob/master/src/app/cache/mailing_list.rs}{\texttt{src/app/cache/mailing\_list.rs}}

\textbf{Dependências:}

\begin{itemize}
    \item \textbf{Lore API}: Para buscar os dados da lista de discussão
    \item \textbf{Sistema de Arquivos}: Para persistir o cache em disco
    \item \textbf{Configurações}: Para obter o caminho do arquivo de cache
\end{itemize}

\textbf{Mensagens:}

\begin{itemize}
    \item \texttt{Get}: Recupera uma única lista de discussão por seu índice na lista ordenada
    \item \texttt{GetSlice}: Recupera um intervalo de listas de discussão para paginação
    \item \texttt{Refresh}: Força uma atualização completa do cache da API
    \item \texttt{Invalidate}: Limpa o cache em memória e em disco
    \item \texttt{IsAvailable}: Verifica se um intervalo de índices está disponível em cache
    \item \texttt{Len}: Retorna o número total de listas de discussão em cache
    \item \texttt{Persist}: Persiste o cache no sistema de arquivos
    \item \texttt{Load}: Carrega o cache do sistema de arquivos
\end{itemize}

\textbf{Feed}

Fornece \emph{cache} por lista de discussão de metadados de \emph{patches} (como autor, assunto e data). Ele busca \emph{feeds} de \emph{patches} sob demanda, suporta paginação e persiste os metadados no sistema de arquivos. Ele usa uma estratégia de validação inteligente para buscar apenas \emph{patches} novos quando um \emph{feed} foi atualizado no servidor.

\textbf{Implementação:} \href{https://github.com/nahharris/ph-actors-tcc/blob/master/src/app/cache/feed.rs}{\texttt{src/app/cache/feed.rs}}

\textbf{Dependências:}

\begin{itemize}
    \item \textbf{Lore API}: Para buscar metadados de patches
    \item \textbf{Sistema de Arquivos}: Para persistir o cache em disco
    \item \textbf{Configurações}: Para obter o caminho do diretório de cache
    \item \textbf{Log}: Para registrar operações de cache
\end{itemize}

\textbf{Mensagens:}

\begin{itemize}
    \item \texttt{Get}: Recupera metadados de um único \emph{patch} por seu índice dentro de um \emph{feed} de lista de discussão
    \item \texttt{GetSlice}: Recupera um intervalo de metadados de \emph{patches} para paginação
    \item \texttt{Refresh}: Atualiza inteligentemente o \emph{cache} para uma lista de discussão específica, buscando apenas itens novos
    \item \texttt{Invalidate}: Limpa o \emph{cache} para uma lista de discussão específica
    \item \texttt{IsAvailable}: Verifica se um intervalo de índices está disponível em \emph{cache} para uma lista
    \item \texttt{Len}: Retorna o número de entradas de metadados em \emph{cache} para uma lista
    \item \texttt{Persist}: Persiste o \emph{cache} de uma lista no sistema de arquivos
    \item \texttt{Load}: Carrega o \emph{cache} de uma lista do sistema de arquivos
    \item \texttt{IsLoaded}: Verifica se o \emph{cache} de uma lista foi carregado do disco
\end{itemize}

\textbf{Patches}

Armazena em \emph{cache} o conteúdo bruto de \emph{patches} individuais (formato \texttt{.mbox}). Como o conteúdo do \emph{patch} é imutável, uma vez que um \emph{patch} é buscado e armazenado em \emph{cache}, ele é considerado válido para sempre. Este ator armazena cada \emph{patch} em um arquivo separado no disco e usa um \emph{buffer} LRU (\emph{Least Recently Used}) em memória para fornecer acesso rápido a \emph{patches} visualizados recentemente.

\textbf{Implementação:} \href{https://github.com/nahharris/ph-actors-tcc/blob/master/src/app/cache/patch.rs}{\texttt{src/app/cache/patch.rs}}

\textbf{Dependências:}

\begin{itemize}
    \item \textbf{Lore API}: Para buscar o conteúdo bruto do patch
    \item \textbf{Sistema de Arquivos}: Para armazenar arquivos de patch permanentemente
    \item \textbf{Configurações}: Para obter o caminho do diretório de cache
    \item \textbf{Log}: Para registrar operações de cache
\end{itemize}

\textbf{Mensagens:}

\begin{itemize}
    \item \texttt{Get}: Recupera o conteúdo bruto de um \emph{patch} dado sua lista de discussão e ID de mensagem (busca da \emph{API} se não estiver em \emph{cache})
    \item \texttt{Invalidate}: Remove um \emph{patch} específico do \emph{cache} em disco e \emph{buffer} em memória
    \item \texttt{IsAvailable}: Verifica se um \emph{patch} está em \emph{cache} sem buscá-lo
\end{itemize}

\subsubsection{App}

O ator App atua como entidade central da aplicação, gerenciando o ciclo de vida e estado da aplicação. Ele é responsável pela inicialização da aplicação, processamento de eventos de UI do Terminal e encerramento gracioso quando apropriado.

\textbf{Implementação:} \href{https://github.com/nahharris/ph-actors-tcc/blob/master/src/app.rs}{\texttt{src/app.rs}}

\textbf{Dependências:}

\begin{itemize}
    \item \textbf{Mailing List Cache}: Para gerenciar o cache de listas de discussão
    \item \textbf{Feed Cache}: Para gerenciar o cache dos feeds das listas de patches
    \item \textbf{Terminal}: Para receber eventos de UI capturados pelo terminal
    \item \textbf{UI}: Para atualizar a interface de usuário com base nas ações do usuário
    \item \textbf{Log}: Para registrar operações da aplicação
\end{itemize}

\textbf{Mensagens:}

\begin{itemize}
    \item \texttt{Shutdown}: Inicia o processo de encerramento graceful da aplicação
\end{itemize}

Note que os eventos de teclado são registrados pelo Terminal e processados pelo App. Todavia isto não é feito com uma mensagem enviada pelo Terminal para o App, mas sim o App que vai solicitar os eventos de \emph{UI} ao Terminal no momento apropriado. Caso contrário, existiria um ciclo de dependências entre o Terminal e o App. Pois o App depende de Ui, que por sua vez depende de Terminal. Caso o Terminal tivesse de enviar mensagens ao App, então o Terminal dependeria do App, fechando o ciclo. Na presente proposta, as dependências precisam ser organizadas sem ciclos.
