\chapter{Proposta de Modelos de Atores em Rust}

Uma das principais contribuições deste trabalho é a proposta de um \emph{framework} para aplicações centralizadas escritas em Rust usando o Modelo de Atores. Uma vez que a teoria sobre o Modelo de Atores e as implementações conhecidas foram discutidas, é hora de adaptar suas abstrações para as necessidades e características específicas de aplicações centralizadas em Rust.

\section{Rust}

O Modelo de Atores é amplamente conhecido por sua dinamicidade e flexibilidade, com a maioria de suas implementações famosas sendo em runtimes flexíveis como BEAM ou JVM. Rust é bem o oposto disso, uma linguagem moderna com um sistema de tipos forte e um compilador poderoso o suficiente para validar quase tudo em tempo de compilação.

Pode soar contraditório usar uma linguagem rígida com um padrão flexível, mas é exatamente o propósito deste trabalho: experimentar com o Modelo de Atores fora do seu domínio específico. Assim, além de testar no contexto centralizado, iremos implementá-lo numa tecnologia que não foi pensada pra isso.

Apesar desta distância, Rust ainda possui diversos recursos de linguagem análogos a mecanismos fornecidos por Elixir, fazendo essa adaptação ser possível. Além disso, se Elixir foi eleita a segunda linguagem mais amadas nos últimos 3 anos. A mesma pesquisa aponta Rust como sendo a linguagem mais amada desde 2016. Vale ressaltar que Rust 1.0 foi lançado em 2015.

Rust é conhecido por seus mecanismos de segurança que forçam verificação em tempo de compilação, tornando diversos estados inválidos impossíveis de serem representados como código.

Os conceitos mais importantes aqui são:

\subsection{Segurança de Memória}

Um espaço de memória tem um, e apenas um, proprietário (uma variável), este proprietário determina o ciclo de vida do espaço de memória. Uma vez que o proprietário é destruído, o espaço de memória é liberado. O proprietário também determina se a região é mutável ou não.

\begin{lstlisting}[language=Rust, caption=Declaração de variáveis e mutabilidade]
fn main() {
    let a = 10;
    let mut b = 20;
    
    // a += 1; // Proibido: a não é mutável
    b += 1; // Permitido: b é mutável
    
    // Quando o código termina aqui, a e b são liberados da memória
}
\end{lstlisting}

\begin{lstlisting}[language=Rust, caption=Transferência de propriedade]
fn main() {
    let data = [1, 2, 3, 4]; // Cria variável imutável
    // As duas operações a seguir são proibidas pelo compilador
    // data = [2, 3, 4, 5];
    // data[0] = 0;

    let mut data2 = data; // Variável mutável data2
    // Uso de data proibido pelo compilador desse ponto em diante,
    // já que seu conteúdo foi transferido para data2
    // println!("{}", data[0]); // Erro de compilação

    // Permitido
    data2[0] = 0;
    data2 = [2, 3, 4, 5]; 
}
\end{lstlisting}

Um valor pode ser emprestado com o uso de referências, mas existem regras checadas pelo compilador:

\begin{enumerate}
    \item Referências não podem ser nulas
    \item As referências não podem existir por mais tempo do que o dono original
    \item Podem existir infinitas referências imutáveis (\texttt{\&}) a um valor
    \item Pode existir no máximo uma referência mutável (\texttt{\&mut}) a um valor (desde que ele seja mutável)
    \item Um valor não pode ter ambas referências ao mesmo tempo
\end{enumerate}

\begin{lstlisting}[language=Rust, caption=Referências imutáveis]
fn main() {
    let numbers = vec![1, 2, 3, 4];
    let nref = &numbers;
    println!("{}", nref[1]); // -> 2
    
    // Permitido: múltiplas referências imutáveis
    let nref2 = &numbers;
    
    // Proibido: não pode ter referência mutável 
    // quando já existem referências imutáveis
    // let mref = &mut numbers;
}
\end{lstlisting}

\begin{lstlisting}[language=Rust, caption=Referências mutáveis]
fn main() {
    let mut numbers = vec![1, 2, 3];
    let nref = &mut numbers;
    
    // Permitido: operação mutável usando &mut
    nref.push(4);
    
    // Proibido: só pode haver uma referência mutável
    // let nref2 = &mut numbers;
    
    // Proibido: não pode usar o valor original
    // enquanto existe referência mutável
    // numbers.push(5);
}
\end{lstlisting}

\begin{lstlisting}[language=Rust, caption=Ciclo de vida de referências]
fn main() {
    let numbers = vec![1, 2, 3, 4];
    let nref = &numbers;
    println!("{}", nref[1]); // -> 2
    
    drop(numbers); // Libera numbers da memória
    
    // A partir deste ponto, o compilador proibirá
    // o uso de tanto numbers quanto nref
    // println!("{}", nref[1]); // Erro de compilação
}
\end{lstlisting}

\subsection{Sistema de Tipos}

O sistema de tipos forte e expressivo é uma característica-chave do Rust. Ele não tem herança, mas compensa isso com tuplas, structs, enums e traits.

\subsubsection{Tuplas}

Uma tupla é simplesmente um tipo produto, tem tamanho fixo e cada campo (nomeado por seu índice) pode ter um tipo diferente. Não é uma coleção!

\begin{lstlisting}[language=Rust, caption=Declaração e uso de tuplas]
fn main() {
    let value: (i32, f32) = (20, 3.14);
    println!("{}", value.0); // -> 20
}
\end{lstlisting}

\subsubsection{Structs}

Um struct é similar a uma tupla, mas tem campos nomeados e pode ter métodos com o uso de um bloco \texttt{impl}:

\begin{lstlisting}[language=Rust, caption=Definição e uso de structs]
struct Point {
    timestamp: i32,
    value: f32
}

impl Point {
    // Método que pode mutar o valor de self
    fn add(&mut self, value: f32) {
        self.value += value;
    }
    
    // Método estático que serve como construtor
    fn new(timestamp: i32, value: f32) -> Self {
        Self { timestamp, value } // Sintaxe abreviada
    }
}

fn main() {
    let mut p = Point::new(20, 2.14);
    p.add(1.0);
}
\end{lstlisting}

Existe também um construto chamado tuple-struct que é um struct mas os campos são nomeados por seus índices, como uma tupla:

\begin{lstlisting}[language=Rust, caption=Tuple-struct]
struct Coordinate(i32, i32);

fn main() {
    let origin = Coordinate(0, 0);
}
\end{lstlisting}

\subsubsection{Enums}

Diferente da maioria das linguagens, enums em Rust podem ter payloads já que cada variante pode ser tratada como um struct:

\begin{lstlisting}[language=Rust, caption=Enums com payloads]
enum Coordinate {
    Polar { 
        theta: f32, 
        radius: f32
    },
    Cartesian(f32, f32),
    Origin,
}

fn main() {
    let origin: Coordinate = Coordinate::Origin;
    let point1: Coordinate = Coordinate::Cartesian(1.0, 1.0);
    let point2: Coordinate = Coordinate::Polar { theta: 45.0, radius: 2.0 };
}
\end{lstlisting}

\subsubsection{Traits}

Traits são o equivalente Rust de uma interface, define métodos que devem ser implementados por um tipo para que ele tenha uma dada característica. São úteis para limitar tipos genéricos ou sobrecarregar operadores:

\begin{lstlisting}[language=Rust, caption=Implementação de traits]
use std::fmt::{Display, Formatter, Error};

// Display é um trait usado para formatação de string com {}
impl Display for Coordinate {
    fn fmt(&self, f: &mut Formatter<'_>) -> Result<(), Error> {
        match self {
            Coordinate::Origin => write!(f, "Origin"),
            Coordinate::Cartesian(x, y) => write!(f, "({}, {})", x, y),
            Coordinate::Polar { theta, radius } => 
                write!(f, "{} ({})", radius, theta)
        }
    }
}

fn main() {
    let coord = Coordinate::Polar { radius: 10.0, theta: 75.0 };
    println!("A coordenada é {}", coord); // -> 10 (75)
}
\end{lstlisting}

Com conhecimento básico da linguagem, é momento de começar a introduzir os elementos da proposta em si. Para isso, os elementos da linguagem Elixir que foram discutidos previamente serão usados como referência fortemente.

\section{Concorrência e Paralelismo}

Esta proposta contempla o uso de \emph{green-threads} que não têm suporte nativo em Rust. Isso é porque a linguagem, ao contrário de Elixir, Golang, ou Java, tem um runtime muito mínimo, similar ao runtime do C. O suporte para green-threads é fornecido pela biblioteca Tokio e eles são chamados de \emph{tasks} e serão usados de forma equivalente aos processos Erlang.

As tasks são criadas e executadas com isolamento, seja de forma concorrente ou paralela, dependendo da quantidade de threads do sistema operacional que estão sendo utilizadas pelo ambiente de execução Tokio. Isso permite que múltiplas tasks sejam executadas simultaneamente sem a necessidade de gerenciar manualmente threads do sistema operacional.

\begin{lstlisting}[language=Rust, caption=Exemplo de tasks concorrentes com Tokio]
use tokio;

#[tokio::main]
async fn main() {
    // Gera a primeira task
    let task1 = tokio::spawn(async {
        println!("Task 1 executando!");
    });
    
    // Gera a segunda task
    let task2 = tokio::spawn(async {
        println!("Task 2 executando!");
    });
    
    // Aguarda ambas as tasks terminarem
    let _ = tokio::join!(task1, task2);
}
\end{lstlisting}

No exemplo acima, duas tasks são criadas usando \texttt{tokio::spawn}, cada uma executando de forma independente e concorrente (sem garantia de ordenação). A função \texttt{tokio::join!} aguarda que ambas as tasks sejam concluídas antes de prosseguir.

Similarmente ao que foi aprensentado nos exemplos com Elixir, onde um ator teria um processo dedicado para lidar com a lógica de processamento de mensagens, aqui será feito uso de \emph{tasks} para isso.

\section{Compartilhamento de Memória}

O isolamento de memória é desejável e uma característica nativa do Modelo de Atores, já que atores são projetados para executar em ambientes físicamente isolados. Isso aumenta a segurança, mas pode degradar a performance já que o compartilhamento de dados entre máquinas remotas só pode ser feito por cópia.

Mas esse não é o caso para esta proposta, já que a aplicação não é distribuída, temos a garantia que a memória sempre pode ser compartilhada. Além disso, os problemas com compartilhamento de memória em sistemas concorrentes estão geralmente relacionados a condições de corrida e mutabilidade indesejada. 

Assim como Elixir garante a imutabilidade dos valores para impedir condições de corrida na comunicação entre processos, Rust e Tokio fornece diversos mecanismos nativos eficientes para compartilhar espaços de memória de forma segura entre \emph{tasks}. Desse modo, usando a abstração correta no cenário correto, é possível de se obter resultados interessantes.

O tipo \texttt{Arc<T>} será o principal utilizado para dados complexos, já que permite que um espaço de memória imutável seja compartilhado com contagem de referência atômica (uma vez que ninguém está referenciando-o, ele é liberado). Isso garante que múltiplas tasks possam acessar os mesmos dados de forma segura sem a necessidade de cópia.

\section{Passagem de Mensagens e Endereços}

Tanto Rust quanto Tokio têm uma abstração nativa de passagem de mensagens chamada de canal. Ao contrário da função \texttt{send} do Elixir que recebe como parametros um endereço e um dado qualquer como mensagem, o método \texttt{send} dos canais são fortemente tipados quanto a mensagem e usam um endereço bem definido.

Existem alguns tipos diferentes de canais. Os 2 principais tipos para o escopo deste trabalho são:

\subsection{\texttt{mpsc} - \emph{Multiple producer, single consumer}}

Um canal de múltiplos produtores, consumidor único é a abstração que será usada como endereço de ator. Ele tem 2 extremidades: \texttt{Sender} e \texttt{Receiver}. O \texttt{Sender} pode ser compartilhado entre todos os atores que querem se comunicar com um ator particular apenas criando uma duplicata com o método \texttt{clone}. A extremidade \texttt{Receiver} é única e será mantida na \emph{task} onde a lógica do ator se encontra e receberá mensagens até o canal ser fechado, ou seja, até não existirem mais clones da extremidade \texttt{Sender} correspondente.

Note que o principio de localidade e segurança do Modelo de Atores nos garante que ninguém deve ser capaz de descobrir o endereço de um ator sem que esse tenha lhe sido dado. Portanto, no momento que não existem mais extremidades \texttt{Sender} a um ator, este garantidamente não receberá mais nenhuma mensagem e pode ser finalizado. Isso acontece de forma natural em Rust com o uso de um loop, enquanto que em Elixir um ator não recebe nenhum indicativo que seu endereço se tornou desconhecido.

\begin{lstlisting}[language=Rust, caption=Exemplo de loop de recebimento de mensagens]
// Loop que processa mensagens até o canal ser fechado
while let Some(message) = rx.recv().await {
    match message {
        Message::SetThing { value } => {
            println!("Definindo valor: {}", value);
        }
        Message::GetThing { tx } => {
            let _ = tx.send(42); // Envia resposta
        }
    }
}
// Quando não há mais Senders, rx.recv() retorna None
// e o loop se encerra automaticamente
println!("Ator finalizando - canal fechado");
\end{lstlisting}

No exemplo acima, o loop \texttt{while let Some(message) = rx.recv().await} continuará processando mensagens enquanto houver extremidades \texttt{Sender} ativas. Quando todas as extremidades \texttt{Sender} são descartadas (saem de escopo ou são explicitamente liberadas com o uso de \texttt{drop}), o método \texttt{recv()} retorna \texttt{None}, fazendo com que o loop se encerre naturalmente e a task do ator seja finalizada.

Em Elixir, o equivalente seria:

\begin{lstlisting}[language=ruby, caption=Exemplo equivalente em Elixir]
def loop do
    receive do
        {:set_thing, value} ->
        IO.puts("Definindo valor: #{value}")
        loop()
        {:get_thing, sender} ->
        send(sender, {:ok, 42})
        loop()
    end
end
\end{lstlisting}

Exemplo acima, em Elixir, é um ator que pode se tornar um ator zumbi, ou seja, que está consumindo recursos ainda que não seja mais usado. Para resolver isso é necessário o uso de um timeout ou de uma mensagem que indique ao ator que ele pode terminar.

É importante notar que o Rust garante, em tempo de compilação, que o receptor de um canal é único. Assim, é garantido que as mensagens chegam ao destino correto. Além disso, o canal tem uma fila com tamanho configurável, e é garantido que a mensagem chegará se a fila não estiver cheia.

\subsection{oneshot}

Um canal que é destruído após uma mensagem ser enviada. Como os canais são unidirecionais, se uma mensagem enviada precisar de uma resposta, um canal oneshot deverá ser criado para envio da resposta.

Também vale ressaltar que o "uso após liberação" de um canal oneshot é verificado em tempo de compilação.


\section{Representação do Ator}

Uma vez definidas quais abstrações a serem usadas, é hora de definir como um ator será em termos de código Rust. 

Primeiramente, haverá um módulo para cada ator, e se um ator é subordinado à existência de outro ator pela lógica de negócio, ele pode ser criado como um submódulo.

Neste trabalho, o padrão para módulos será ter um arquivo e uma pasta com o mesmo nome (exceto pela extensão \texttt{.rs}). Por exemplo, para um ator chamado App, deve haver um \texttt{app.rs} e uma pasta \texttt{app/} no mesmo diretório.

Até aqui, três partes principais de um ator foram apresentadas:

\begin{itemize}
    \item As mensagens que serão enviadas ao ator
    \item A lógica de processamento das mensagens recebidas
    \item O endereço que permite a comunicação entre atores
\end{itemize}

Essas três partes serão traduzidas para partes separadas do código Rust como:

\begin{itemize}
    \item Um enum privado para definir os tipos das mensagens
    \item Uma struct privada para gerenciar o estado do ator e definir como lidar com cada mensagem
    \item Uma struct pública para abstrair o canal \emph{mpsc} que serve como o endereço
\end{itemize}

Para o exemplo do ator App, haverá:

\begin{itemize}
    \item Um enum \texttt{Message} em \texttt{app/message.rs} definindo o tipo para as mensagens
    \item Uma struct \texttt{Core} em \texttt{app/core.rs} que mantém a lógica do ator
    \item Uma struct \texttt{App} em \texttt{app.rs} para servir como a interface pública para dependentes deste ator
\end{itemize}

Onde \texttt{App} deve ser público globalmente, enquanto \texttt{Message} e \texttt{Core} ficam restritos ao super-módulo \texttt{app}.

Note que a convenção é que a struct que serve como interface pública para o ator será nomeada com o nome efetivo do ator para melhor legibilidade. Esta chamada interface pública deve fornecer métodos que abstraem a lógica de construção de mensagens e utilização de canais.

A seguir está destrinchado em mais detalhes o que estará em cada uma das 3 partes.

\subsection{Mensagens}

Assim como tudo em Rust, as mensagens enviadas através de canais devem ser tipadas. Caso um ator só execute um tipo de ação, ou seja, só receba um tipo de mensagem então qualquer tipo pode ser usado para representar as mensagens. Caso ele lide com diferentes tipos de mensagens (o que acontece na maioria dos casos) um \emph{enum} será usado.

No contexto do exemplo dado, o \emph{enum} a ser criado no arquivo \texttt{app/message.rs} seria:

\begin{lstlisting}[language=Rust, caption=Exemplo de mensagens tipadas]
enum Message {
    SetThing { value: i32 }, 
    GetThing { tx: oneshot::Sender<i32> }
}
\end{lstlisting}

A maior vantagem de tipar mensagens com \emph{enums} é que o envio e o tratamento são verificados em tempo de compilação. Isso cria uma garantia forte sobre quais mensagens que podem estar envolvidas em uma dada comunicação e o compilador Rust garantirá que:

\begin{itemize}
    \item O receptor fornecerá tratamento explícito para todas as mensagens possíveis
    \item O remetente nunca enviará uma mensagem inválida
\end{itemize}

As garantias acima não se aplicam à implementação do Modelo de Atores em Elixir. 

\subsection{Lógica}

Toda a lógica de processamento de mensagens para um ator ficará dentro de uma \emph{struct} chamada de \texttt{Core}. Ela será também onde será feito o gerenciamento de estado do ator e pelos detalhes específicos para criação da \emph{task} e do canal \texttt{mpsc} dedicado para a comunicação.

No contexto do exemplo dado, a \emph{struct} a ser criada no arquivo \texttt{app/core.rs} seria:

\begin{lstlisting}[language=Rust, caption=Exemplo de struct Core para lógica do ator]
pub struct Core {
    thing: i32,
}
\end{lstlisting}


O \texttt{Core} deve ser instanciado com a invocação do seu construtor, nesse momento as dependências do ator deverão ser injetadas como argumentos do construtor. O construtor será chamado \texttt{new} caso não possa falhar, caso contrário será chamado de \texttt{build}. Por exemplo, a inicialização de um ator pode depender do valor de uma variável de ambiente que talvez não exista, e isso leva a uma falha.

\begin{lstlisting}[language=Rust, caption=Exemplo de construtor]
impl Core {
    pub fn new(thing: i32) -> Self {
        Self {
            thing
        }
    }
}
\end{lstlisting}

Deverá ser fornecido um método de instância \texttt{init} responsável por conter a lógica de processamento das mensagens recebidas, delegando elas para os métodos responsáveis.

\begin{lstlisting}[language=Rust, caption=Exemplo de construtor]
    impl Core {
        // ...
        pub async fn init(mut self, mut rx: mpsc::Receiver<Message>) {
            while let Some(message) = rx.recv().await {
                match message {
                    Message::SetThing { value } => {
                        self.handle_set_thing(value);
                    }
                    Message::GetThing { tx } => {
                        let result = self.handle_get_thing();
                        let _ = tx.send(result);
                    }
                }
            }
        }
        
        fn handle_set_thing(&mut self, value: i32) {
            self.thing = value;
        }
        
        fn handle_get_thing(&self) -> i32 {
            self.thing
        }
    }
\end{lstlisting}

Note que o método \texttt{init} recebe \texttt{self} como primeiro argumento, isso significa que ele consome a instância. Em outras palavras, aquele que tiver posse de uma instância do \texttt{Core} do App a perderá assim que \texttt{init} for invocada, impedindo que um mesmo objeto seja instanciado como 2 atores compartilhando o mesmo espaço de memória. O segundo parâmetro é a ponta de recebimento de mensagens do canal para se comunicar com o ator.

Adicionalmente, cada ramo do bloco \texttt{match} apenas obtém os valores da mensagem e delega a execução para um método privado \texttt{handle\_}. Em caso de necessidade de enviar resposta, isso não deve ser feito dentro método \texttt{handle}, assegurando assim o princípio de responsabilidade única.

\subsection{Endereço}

Para se aproveitar ao máximo dos recursos que a linguagem Rust oferece, é ideal a criação de um tipo que abstraia a lógica de uso dos canais, tanto para facilitar a leitura do código, quanto para diminuir duplicação de código. Ao contrário do que é feito em Elixir, onde se atribui o nome do ator ao módulo onde se encontra a lógica de processamento, aqui o nome será atribuído a essa abstração sobre o endereço.

\begin{lstlisting}[language=Rust, caption=Exemplo de struct para endereço do ator]
use tokio::sync::{mpsc, oneshot};
use crate::error::{AppError, FatalActorError};

pub struct App {
    tx: mpsc::Sender<Message>,
}

impl App {
    pub fn spawn(value: i32) -> Self {
        let (tx, rx) = mpsc::channel(crate::BUFFER_SIZE);
        let core = Core::new(value);
        let _ = tokio::spawn(async move {
            core.init(rx).await;
        });

        Self { tx }
    }

    pub async fn thing(&self) -> Result<i32, AppError> {
        let (tx, rx) = oneshot::channel();
        let message = Message::GetThing { tx };
        
        self.tx.send(message).await
            .map_err(|_| {
                AppError::Fatal(FatalActorError::ActorSendFailed {
                    actor_name: "App",
                    operation: "get thing".to_string(),
                })
            })?;
        
        rx.await
            .map_err(|_| {
                AppError::Fatal(FatalActorError::ActorRecvFailed {
                    actor_name: "App",
                    operation: "get thing".to_string(),
                })
            })?
    }
    
    pub async fn thing_alt(&self) -> Result<oneshot::Receiver<Result<i32, AppError>>, AppError> {
        let (tx, rx) = oneshot::channel();
        let message = Message::GetThing { tx };
        
        self.tx.send(message).await
            .map_err(|_| {
                AppError::Fatal(FatalActorError::ActorSendFailed {
                    actor_name: "App",
                    operation: "get thing".to_string(),
                })
            })?;
        
        Ok(rx)
    }
    
    pub async fn set_thing(&self, value: i32) -> Result<(), AppError> {
        let message = Message::SetThing { value };
        
        self.tx.send(message).await
            .map_err(|_| {
                AppError::Fatal(FatalActorError::ActorSendFailed {
                    actor_name: "App",
                    operation: "set thing".to_string(),
                })
            })
    }
}
\end{lstlisting}

No exemplo acima, a struct \texttt{App} encapsula o \texttt{Sender} do canal \texttt{mpsc} e fornece métodos públicos que abstraem completamente a lógica de envio de mensagens. O método \texttt{thing()} cria um canal \texttt{oneshot} para receber a resposta, envia a mensagem \texttt{GetThing} e aguarda a resposta. O método \texttt{thing\_alt()} oferece uma alternativa onde retorna o \texttt{Receiver} diretamente, permitindo que o invocador decida quando aguardar pela resposta. O método \texttt{set\_thing()} simplesmente envia a mensagem \texttt{SetThing} com o valor fornecido.

Essa abstração permite que outros atores interajam com o ator sem precisar se preocupar com detalhes de comunicação por canais, mantendo a interface limpa e tipada.

\section{Tratamento de Erros}

Um aspecto fundamental do modelo de atores proposto é o tratamento de erros de forma consistente e tipada. Diferente de linguagens como Elixir, onde erros são tratados principalmente através de padrões de matching com tuplas \texttt{\{:ok, value\}} ou \texttt{\{:error, reason\}}, Rust oferece o tipo \texttt{Result<T, E>} que força, em tempo de compilação, o tratamento explícito de erros.

Para facilitar a definição e manipulação de erros, este trabalho utiliza duas bibliotecas complementares: \texttt{thiserror}, que permite criar hierarquias de tipos de erro usando derive macros, e \texttt{miette}, que fornece diagnósticos ricos e informativos para erros, facilitando o debugging e a experiência do desenvolvedor.

\subsection{Hierarquia de Erros}

O sistema de erros é organizado hierarquicamente, com três níveis principais:

\begin{itemize}
    \item \textbf{Erros Fatais}: Falhas de nível de sistema que indicam que um ator morreu ou que a comunicação falhou de forma irreversível
    \item \textbf{Erros Específicos de Ator}: Cada ator define apenas os erros que ele pode emitir, garantindo uma interface de erro bem definida
\end{itemize}

\subsection{Erros Fatais}

Erros fatais representam falhas de comunicação que não podem ser recuperadas sem reiniciar o componente afetado. Esses erros são comuns a todos os atores e indicam problemas com o sistema de passagem de mensagens:

\begin{lstlisting}[language=Rust, caption=Definição de erros fatais]
use miette::Diagnostic;
use thiserror::Error;

#[derive(Debug, Error, Diagnostic)]
#[error("Fatal actor error")]
pub enum FatalActorError {
    /// Falha ao enviar mensagem para o ator
    #[error("Failed to send message to actor '{actor_name}' for operation '{operation}'")]
    #[diagnostic(
        code(fatal::actor_send_failed),
        help("The message could not be sent to the actor. The actor may have died or the channel may be closed.")
    )]
    ActorSendFailed {
        actor_name: &'static str,
        operation: String,
    },
    
    /// Falha ao receber resposta do ator
    #[error("Failed to receive response from actor '{actor_name}' for operation '{operation}'")]
    #[diagnostic(
        code(fatal::actor_recv_failed),
        help("The response could not be received from the actor. The actor may have died or the channel may be closed.")
    )]
    ActorRecvFailed {
        actor_name: &'static str,
        operation: String,
        #[source]
        source: tokio::sync::oneshot::error::RecvError,
    },
}
\end{lstlisting}

Erros fatais ocorrem quando o canal de comunicação é fechado, o que acontece quando não há mais extremidades \texttt{Sender} ativas para o ator. Isso pode indicar que o ator terminou inesperadamente ou que todas as referências a ele foram liberadas.

\subsection{Erros Específicos de Ator}

Cada ator define seu próprio tipo de erro, que encapsula tanto os erros específicos do domínio quanto os erros fatais de comunicação. Por exemplo, o ator (\texttt{Env}) define:

\begin{lstlisting}[language=Rust, caption=Exemplo de erro específico de ator]
#[derive(Debug, Error, Diagnostic)]
pub enum EnvError {
    /// Variável de ambiente não encontrada
    NotFound {
        name: String,
    },
    
    /// Erro fatal ocorrido durante operações do ator
    #[error(transparent)]
    #[diagnostic(transparent)]
    Fatal(#[from] FatalActorError),
}
\end{lstlisting}

A variante \texttt{Fatal} permite que erros fatais sejam propagados automaticamente através do operador \texttt{?}, mantendo a hierarquia de erros enquanto permite tratamento específico quando necessário.

\subsection{Propagação de Erros através de Canais}

Quando um ator precisa retornar um resultado que pode falhar, o tipo de retorno deve ser \texttt{Result<T, E>}, onde \texttt{E} é o tipo de erro específico do ator. O resultado é enviado através do canal \texttt{oneshot} como parte da resposta:

\begin{lstlisting}[language=Rust, caption=Processamento de mensagens com tratamento de erros]
impl Core {
    pub async fn init(self, mut rx: mpsc::Receiver<Message>) {
        while let Some(msg) = rx.recv().await {
            match msg {
                Message::Get { tx, key } => {
                    // Processa a operação e pode retornar um erro
                    let result = self.handle_get_env(key);
                    let _ = tx.send(result);
                }
                // ...
            }
        }
    }
    
    fn handle_get_env(&self, key: ArcOsStr) -> Result<ArcStr, EnvError> {
        std::env::var(key.as_ref())
            .map(|s| ArcStr::from(&s))
            .map_err(|_| EnvError::NotFound {
                name: key.to_string_lossy().to_string(),
            })
    }
}
\end{lstlisting}

\subsection{Tratamento de Erros na Interface Pública}

Na interface pública do ator, erros podem ocorrer em dois pontos:

\begin{enumerate}
    \item Ao enviar a mensagem para o ator (falha de comunicação)
    \item Ao receber a resposta do ator (falha de comunicação ou erro de domínio)
\end{enumerate}

Ambos os casos devem ser tratados e convertidos em erros fatais quando apropriado:

\begin{lstlisting}[language=Rust, caption=Tratamento de erros na interface pública do ator]
impl Env {
    pub async fn env(&self, key: ArcOsStr) -> Result<ArcStr, EnvError> {
        let (tx, rx) = tokio::sync::oneshot::channel();
        
        // Erro ao enviar mensagem -> Erro fatal
        self.tx
            .send(Message::Get { tx, key })
            .await
            .map_err(|_e| {
                EnvError::Fatal(FatalActorError::ActorSendFailed {
                    actor_name: "Env",
                    operation: "get environment variable".to_string(),
                })
            })?;
        
        // Erro ao receber resposta -> Erro fatal ou erro de domínio
        rx.await
            .map_err(|e| {
                EnvError::Fatal(FatalActorError::ActorRecvFailed {
                    actor_name: "Env",
                    operation: "get environment variable".to_string(),
                    source: e,
                })
            })?
    }
}
\end{lstlisting}

Note que o operador \texttt{?} é usado para propagar erros automaticamente. Se o envio da mensagem falhar (por exemplo, porque o canal foi fechado), o erro é convertido em um \texttt{FatalActorError}. Se a recepção falhar, também é convertido em um erro fatal. Caso contrário, o resultado (que pode conter um erro de domínio como \texttt{NotFound}) é retornado.

\subsection{Erros Recuperáveis e Não-Recuperáveis}

O sistema distingue entre erros recuperáveis e não-recuperáveis através de um atributo \texttt{retryable} que indica se a operação pode ser tentada novamente.

Essa distinção permite que a aplicação tome decisões inteligentes sobre como lidar com erros, como implementar retry automático para erros, ou desligar graciosamente para erros fatais.

\subsection{Funções Auxiliares para Criação de Erros}

Para simplificar a criação de erros específicos de domínio a partir de erros de bibliotecas externas, o sistema fornece funções auxiliares. Por exemplo, para converter erros de IO do sistema de arquivos em \texttt{FsError}:

\begin{lstlisting}[language=Rust, caption=Função auxiliar para criação de erros de sistema de arquivos]
pub fn fs_error(
    path: Option<impl Into<String>>,
    operation: impl Into<String>,
    source: std::io::Error,
) -> FsError {
    FsError::OperationFailed {
        path: path.map(|p| p.into()),
        operation: operation.into(),
        retryable: source.is_retryable(),
        source,
    }
}
\end{lstlisting}

Essas funções auxiliares garantem que informações relevantes sobre o contexto do erro sejam preservadas e que a informação sobre recuperabilidade seja determinada automaticamente baseada nas características do erro subjacente.

\section{Testabilidade e Mocks}

Uma das principais vantagens da arquitetura baseada em atores é a facilidade de testar componentes isoladamente. Como cada ator possui dependências injetadas através de suas interfaces, é possível substituir dependências reais por implementações mockadas durante os testes.

\subsection{Mockall}

Para simplificar a criação de mocks, este trabalho faz uso da biblioteca \texttt{mockall}, que gera automaticamente implementações mock a partir de traits ou structs. Isso elimina a necessidade de escrever manualmente código boilerplate para mocks e garante que os mocks permaneçam sincronizados com as interfaces reais. O código para mock de um ator deve ser colocado no arquivo \texttt{mock.rs} do módulo do ator e o módulo deve ser declarado como:

\begin{lstlisting}[language=Rust, caption=Exemplo de declaração de módulo para mock]
#[cfg(test)]
pub mod mock;
\end{lstlisting}

Desse modo, o código do mock não será incluso no binário de produção.

\begin{lstlisting}[language=Rust, caption=Exemplo de mock usando mockall]
mock!{
    #[derive(Debug)]
    pub App {
        pub async fn operation(&self, params: Params) -> Result<Value>;
    }

    impl Clone for Actor {
        fn clone(&self) -> Self;
    }
}
\end{lstlisting}

A macro \texttt{mock!} do mockall gera automaticamente uma estrutura com nome \texttt{MockApp} que implementa todos os métodos especificados e permite configurar comportamentos esperados para cada invocação. Além disso, a macro gera implementações de traits como \texttt{Debug} e \texttt{Clone}, mantendo a compatibilidade com a interface original.

\subsection{Integração de Mocks}

Para permitir a substituição fácil entre implementações reais e mockadas, o sistema usa atributos de compilação condicional (\texttt{\#[cfg(test)]} e \texttt{\#[cfg(not(test))]}) para alternar entre as implementações:

\begin{lstlisting}[language=Rust, caption=Alternância entre implementações reais e mockadas]
#[cfg(not(test))]
use crate::other_actor::OtherActor;

#[cfg(test)]
use crate::other_actor::mock::MockOtherActor as OtherActor;

pub struct App {
    dependency: OtherActor,
}

impl App {
    pub fn new(dependency: OtherActor) -> Self {
        Self { dependency }
    }
}
\end{lstlisting}

Durante a compilação normal, o sistema usa a implementação real \texttt{OtherActor}. Durante a compilação de testes, automaticamente substitui por \texttt{MockOtherActor}. Com o uso de compilação condicional, é possível implementar uma infraestrutura de testes bastante robusta que terá nenhum impacto no código de produção.

\subsection{Testes Unitários}

Com mocks em vigor, escrever testes unitários torna-se direto. Cada teste pode configurar o comportamento esperado de suas dependências mockadas e verificar que o ator sob teste se comporta corretamente:

\begin{lstlisting}[language=Rust, caption=Exemplo de teste unitário com mocks]
#[tokio::test]
async fn test_my_actor_operation() {
    let mut mock_dep = MockOtherActor::new();
    mock_dep
        .expect_get_value()
        .times(1)
        .returning(|| Ok(42));
    
    let actor = App::spawn(mock_dep);
    let result = actor.operation().await;
    
    assert_eq!(result, Ok(42));
}
\end{lstlisting}

Os mocks permitem testar tanto cenários de sucesso quanto de falha, validando o tratamento de erros e garantindo que as interações entre atores funcionam corretamente em isolamento.
