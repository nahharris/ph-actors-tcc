\chapter{Proposta de Modelos de Atores em Rust}

Uma das principais contribuições deste trabalho é a proposta de um \emph{framework} para aplicações centralizadas escritas em Rust usando o Modelo de Atores. Uma vez que a teoria sobre o Modelo de Atores e as implementações conhecidas foram discutidas, é hora de adaptar suas abstrações para as necessidades e características específicas de aplicações centralizadas em Rust.

\section{Rust}

O Modelo de Atores é amplamente conhecido por sua dinamicidade e flexibilidade, com a maioria de suas implementações famosas sendo em runtimes flexíveis como BEAM ou JVM. Rust é bem o oposto disso, uma linguagem moderna com um sistema de tipos forte e um compilador poderoso o suficiente para validar quase tudo em tempo de compilação.

Pode soar contraditório usar uma linguagem rígida com um padrão flexível, mas é exatamente o propósito deste trabalho: experimentar com o Modelo de Atores fora do seu domínio específico. Assim, além de testar no contexto centralizado, iremos implementá-lo numa tecnologia que não foi pensada pra isso.

Apesar desta distância, Rust ainda possui diversos recursos de linguagem análogos a mecanismos fornecidos por Elixir, fazendo essa adaptação ser possível. Além disso, se Elixir foi eleita a segunda linguagem mais amadas nos últimos 3 anos. A mesma pesquisa aponta Rust como sendo a linguagem mais amada desde 2016. Vale ressaltar que Rust 1.0 foi lançado em 2015.

Rust é conhecido por seus mecanismos de segurança que forçam verificação em tempo de compilação, tornando diversos estados inválidos impossíveis de serem representados como código.

\section{Concorrência e Paralelismo}

Esta proposta contempla o uso de \emph{green-threads} que não têm suporte nativo em Rust. Isso é porque a linguagem, ao contrário de Elixir, Golang, ou Java, tem um runtime muito mínimo, similar ao runtime do C. O suporte para green-threads é fornecido pela biblioteca Tokio e eles são chamados de \emph{tasks} e serão usados de forma equivalente aos processos Erlang.

As tasks são criadas e executadas com isolamento, seja de forma concorrente ou paralela, dependendo da quantidade de threads do sistema operacional que estão sendo utilizadas pelo ambiente de execução Tokio. Isso permite que múltiplas tasks sejam executadas simultaneamente sem a necessidade de gerenciar manualmente threads do sistema operacional.

\begin{program}
  \lstinputlisting[
    language=Rust,
  ]{conteudo/codigo/rust-tasks-tokio.rs}
  \caption{Exemplo de tasks concorrentes com Tokio.\label{prog:rust-tasks-tokio}}
\end{program}

No exemplo acima, duas tasks são criadas usando \texttt{tokio::spawn}, cada uma executando de forma independente e concorrente (sem garantia de ordenação). A função \texttt{tokio::join!} aguarda que ambas as tasks sejam concluídas antes de prosseguir.

Similarmente ao que foi aprensentado nos exemplos com Elixir, onde um ator teria um processo dedicado para lidar com a lógica de processamento de mensagens, aqui será feito uso de \emph{tasks} para isso.

\section{Compartilhamento de Memória}

O isolamento de memória é desejável e uma característica nativa do Modelo de Atores, já que atores são projetados para executar em ambientes físicamente isolados. Isso aumenta a segurança, mas pode degradar a performance já que o compartilhamento de dados entre máquinas remotas só pode ser feito por cópia.

Mas esse não é o caso para esta proposta, já que a aplicação não é distribuída, temos a garantia que a memória sempre pode ser compartilhada. Além disso, os problemas com compartilhamento de memória em sistemas concorrentes estão geralmente relacionados a condições de corrida e mutabilidade indesejada. 

Assim como Elixir garante a imutabilidade dos valores para impedir condições de corrida na comunicação entre processos, Rust e Tokio fornece diversos mecanismos nativos eficientes para compartilhar espaços de memória de forma segura entre \emph{tasks}. Desse modo, usando a abstração correta no cenário correto, é possível de se obter resultados interessantes.

O tipo \texttt{Arc<T>} será o principal utilizado para dados complexos, já que permite que um espaço de memória imutável seja compartilhado com contagem de referência atômica (uma vez que ninguém está referenciando-o, ele é liberado). Isso garante que múltiplas tasks possam acessar os mesmos dados de forma segura sem a necessidade de cópia.

\section{Passagem de Mensagens e Endereços}

Tanto Rust quanto Tokio têm uma abstração nativa de passagem de mensagens chamada de canal. Ao contrário da função \texttt{send} do Elixir que recebe como parametros um endereço e um dado qualquer como mensagem, o método \texttt{send} dos canais são fortemente tipados quanto a mensagem e usam um endereço bem definido.

Existem alguns tipos diferentes de canais. Os 2 principais tipos para o escopo deste trabalho são:

\subsection{\texttt{mpsc} - \emph{Multiple producer, single consumer}}

Um canal de múltiplos produtores, consumidor único é a abstração que será usada como endereço de ator. Ele tem 2 extremidades: \texttt{Sender} e \texttt{Receiver}. O \texttt{Sender} pode ser compartilhado entre todos os atores que querem se comunicar com um ator particular apenas criando uma duplicata com o método \texttt{clone}. A extremidade \texttt{Receiver} é única e será mantida na \emph{task} onde a lógica do ator se encontra e receberá mensagens até o canal ser fechado, ou seja, até não existirem mais clones da extremidade \texttt{Sender} correspondente.

Note que o principio de localidade e segurança do Modelo de Atores nos garante que ninguém deve ser capaz de descobrir o endereço de um ator sem que esse tenha lhe sido dado. Portanto, no momento que não existem mais extremidades \texttt{Sender} a um ator, este garantidamente não receberá mais nenhuma mensagem e pode ser finalizado. Isso acontece de forma natural em Rust com o uso de um loop, enquanto que em Elixir um ator não recebe nenhum indicativo que seu endereço se tornou desconhecido.

\begin{program}
  \lstinputlisting[
    language=Rust,
  ]{conteudo/codigo/rust-loop-mensagens.rs}
  \caption{Exemplo de loop de recebimento de mensagens.\label{prog:rust-loop-mensagens}}
\end{program}

No exemplo acima, o loop \texttt{while let Some(message) = rx.recv().await} continuará processando mensagens enquanto houver extremidades \texttt{Sender} ativas. Quando todas as extremidades \texttt{Sender} são descartadas (saem de escopo ou são explicitamente liberadas com o uso de \texttt{drop}), o método \texttt{recv()} retorna \texttt{None}, fazendo com que o loop se encerre naturalmente e a task do ator seja finalizada.

Em Elixir, o equivalente seria:

\begin{program}
  \lstinputlisting[
    language=Elixir,
  ]{conteudo/codigo/elixir-loop-equivalente.ex}
  \caption{Exemplo equivalente em Elixir.\label{prog:elixir-loop-equivalente}}
\end{program}

Exemplo acima, em Elixir, é um ator que pode se tornar um ator zumbi, ou seja, que está consumindo recursos ainda que não seja mais usado. Para resolver isso é necessário o uso de um timeout ou de uma mensagem que indique ao ator que ele pode terminar.

É importante notar que o Rust garante, em tempo de compilação, que o receptor de um canal é único. Assim, é garantido que as mensagens chegam ao destino correto. Além disso, o canal tem uma fila com tamanho configurável, e é garantido que a mensagem chegará se a fila não estiver cheia.

\subsection{oneshot}

Um canal que é destruído após uma mensagem ser enviada. Como os canais são unidirecionais, se uma mensagem enviada precisar de uma resposta, um canal oneshot deverá ser criado para envio da resposta.

Também vale ressaltar que o "uso após liberação" de um canal oneshot é verificado em tempo de compilação.


\section{Representação do Ator}

Uma vez definidas quais abstrações a serem usadas, é hora de definir como um ator será em termos de código Rust.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.8\textwidth]{figuras/actor-design.png}
    \caption{Representação da estrutura de um ator}
    \label{fig:actor-design}
\end{figure}

Primeiramente, haverá um módulo para cada ator, e se um ator é subordinado à existência de outro ator pela lógica de negócio, ele pode ser criado como um submódulo.

Neste trabalho, o padrão para módulos será ter um arquivo e uma pasta com o mesmo nome (exceto pela extensão \texttt{.rs}). Por exemplo, para um ator chamado App, deve haver um \texttt{app.rs} e uma pasta \texttt{app/} no mesmo diretório.

Até aqui, três partes principais de um ator foram apresentadas:

\begin{itemize}
    \item As mensagens que serão enviadas ao ator
    \item A lógica de processamento das mensagens recebidas
    \item O endereço que permite a comunicação entre atores
\end{itemize}

Essas três partes serão traduzidas para partes separadas do código Rust como:

\begin{itemize}
    \item Um enum privado para definir os tipos das mensagens
    \item Uma struct privada para gerenciar o estado do ator e definir como lidar com cada mensagem
    \item Uma struct pública para abstrair o canal \emph{mpsc} que serve como o endereço
\end{itemize}

Para o exemplo do ator App, haverá:

\begin{itemize}
    \item Um enum \texttt{Message} em \texttt{app/message.rs} definindo o tipo para as mensagens
    \item Uma struct \texttt{Core} em \texttt{app/core.rs} que mantém a lógica do ator
    \item Uma struct \texttt{App} em \texttt{app.rs} para servir como a interface pública para dependentes deste ator
\end{itemize}

Onde \texttt{App} deve ser público globalmente, enquanto \texttt{Message} e \texttt{Core} ficam restritos ao super-módulo \texttt{app}.

Note que a convenção é que a struct que serve como interface pública para o ator será nomeada com o nome efetivo do ator para melhor legibilidade. Esta chamada interface pública deve fornecer métodos que abstraem a lógica de construção de mensagens e utilização de canais.

A seguir está destrinchado em mais detalhes o que estará em cada uma das 3 partes.

\subsection{Mensagens}

Assim como tudo em Rust, as mensagens enviadas através de canais devem ser tipadas. Caso um ator só execute um tipo de ação, ou seja, só receba um tipo de mensagem então qualquer tipo pode ser usado para representar as mensagens. Caso ele lide com diferentes tipos de mensagens (o que acontece na maioria dos casos) um \emph{enum} será usado.

No contexto do exemplo dado, o \emph{enum} a ser criado no arquivo \texttt{app/message.rs} seria:

\begin{program}
  \lstinputlisting[
    language=Rust,
  ]{conteudo/codigo/rust-mensagens-tipadas.rs}
  \caption{Exemplo de mensagens tipadas.\label{prog:rust-mensagens-tipadas}}
\end{program}

A maior vantagem de tipar mensagens com \emph{enums} é que o envio e o tratamento são verificados em tempo de compilação. Isso cria uma garantia forte sobre quais mensagens que podem estar envolvidas em uma dada comunicação e o compilador Rust garantirá que:

\begin{itemize}
    \item O receptor fornecerá tratamento explícito para todas as mensagens possíveis
    \item O remetente nunca enviará uma mensagem inválida
\end{itemize}

As garantias acima não se aplicam à implementação do Modelo de Atores em Elixir.

Para se aproveitar ao máximo dos recursos que a linguagem Rust oferece, é ideal a criação de um tipo que abstraia a lógica de uso dos canais, tanto para facilitar a leitura do código, quanto para diminuir duplicação de código. Ao contrário do que é feito em Elixir, onde se atribui o nome do ator ao módulo onde se encontra a lógica de processamento, aqui o nome será atribuído a essa abstração sobre o endereço.

\begin{program}
  \lstinputlisting[
    language=Rust,
  ]{conteudo/codigo/rust-actor-address.rs}
  \caption{Exemplo de struct para endereço do ator.\label{prog:rust-actor-address}}
\end{program}

No exemplo acima, a struct \texttt{App} encapsula o \texttt{Sender} do canal \texttt{mpsc} e fornece métodos públicos que abstraem completamente a lógica de envio de mensagens. O método \texttt{thing()} cria um canal \texttt{oneshot} para receber a resposta, envia a mensagem \texttt{GetThing} e aguarda a resposta. O método \texttt{thing\_alt()} oferece uma alternativa onde retorna o \texttt{Receiver} diretamente, permitindo que o invocador decida quando aguardar pela resposta. Essa abstração permite que outros atores interajam com o ator sem precisar se preocupar com detalhes de comunicação por canais, mantendo a interface limpa e tipada.

\section{Tratamento de Erros}

Um aspecto fundamental do modelo de atores proposto é o tratamento de erros de forma consistente e tipada. Diferente de linguagens como Elixir, onde erros são tratados principalmente através de padrões de matching com tuplas \texttt{\{:ok, value\}} ou \texttt{\{:error, reason\}}, Rust oferece o tipo \texttt{Result<T, E>} que força, em tempo de compilação, o tratamento explícito de erros.

Para facilitar a definição e manipulação de erros, este trabalho utiliza duas bibliotecas complementares: \texttt{thiserror}, que permite criar hierarquias de tipos de erro usando derive macros, e \texttt{miette}, que fornece diagnósticos ricos e informativos para erros, facilitando o debugging e a experiência do desenvolvedor.

\subsection{Hierarquia de Erros}

O sistema de erros é organizado hierarquicamente, com três níveis principais:

\begin{itemize}
    \item \textbf{Erros Fatais}: Falhas de nível de sistema que indicam que um ator morreu ou que a comunicação falhou de forma irreversível
    \item \textbf{Erros Específicos de Ator}: Cada ator define apenas os erros que ele pode emitir, garantindo uma interface de erro bem definida
\end{itemize}

\subsection{Erros Fatais}

Erros fatais representam falhas de comunicação que não podem ser recuperadas sem reiniciar o componente afetado. Esses erros são comuns a todos os atores e indicam problemas com o sistema de passagem de mensagens:

\begin{program}
  \lstinputlisting[
    language=Rust,

  \caption{Definição de erros fatais.\label{prog:rust-fatal-errors}}

Erros fatais ocorrem quando o canal de comunicação é fechado, o que acontece quando não há mais extremidades \texttt{Sender} ativas para o ator. Isso pode indicar que o ator terminou inesperadamente ou que todas as referências a ele foram liberadas.

\subsection{Erros Recuperáveis e Não-Recuperáveis}

O sistema distingue entre erros recuperáveis e não-recuperáveis através de atributos ou da variante \texttt{Fatal}. Essa distinção permite que a aplicação tome decisões inteligentes sobre como lidar com erros, como implementar \textit{retry} automático para erros, ou desligar graciosamente para erros fatais.

A macro \texttt{mock!} do mockall gera automaticamente uma estrutura com nome \texttt{MockApp} que implementa todos os métodos especificados e permite configurar comportamentos esperados para cada invocação. Além disso, a macro gera implementações de traits como \texttt{Debug} e \texttt{Clone}, mantendo a compatibilidade com a interface original.

\subsection{Integração de Mocks}

Para permitir a substituição fácil entre implementações reais e mockadas, deve-se usar atributos de compilação condicional (\texttt{\#[cfg(test)]} e \texttt{\#[cfg(not(test))]}) para alternar entre as implementações:

\begin{program}

    language=Rust,
  ]{conteudo/codigo/rust-mock-integration.rs}
  \caption{Alternância entre implementações reais e mockadas.\label{prog:rust-mock-integration}}
\end{program}

Durante a compilação normal, a implementação real \texttt{OtherActor} é usada. Durante a compilação de testes, automaticamente substitui por \texttt{MockOtherActor}. Com o uso de compilação condicional, é possível implementar uma infraestrutura de testes bastante robusta que terá nenhum impacto no código de produção.
